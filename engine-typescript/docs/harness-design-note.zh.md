# Agent Note: 逐轮技能检索作为 pre-step 插件交付

> 原本是 DeepSeek Harness 的 Agent Note，随它所记录的包一起保存在这里。
> 装进 harness 检出时，复制回 `.agents/notes/implemented/architecture/`。

*对应英文版：[English](harness-design-note.md)。*

## 问题

`dsh-tool-skill` 把每个技能的名称和描述发布在一份工具 schema 中，让模型按名称加载其中一个。在目录较小、模型能从一行描述认出正确名称时，这可行。到了数千条的规模就不再可行：schema 装不下，而且模型必须先知道某个技能存在才能请求它。

拥有大规模语料的部署想要的是反方向——用用户刚写下的内容去检索语料，把匹配到的技能正文直接放到模型面前，不需要一次往返。让这件事真正可用的检索质量并非单一排序函数，而是：一个判断该轮是否需要技能的改写器、若干独立排序再融合的来源，以及一次剔除"排上来了但本 agent 执行不了"的模型调用。

## 决策

`@deepseek-ai/dsh-skill-search` 是挂在 `agent/pre-step` 上的函数插件。它先调用 `next()`，对 `reject` 决策原样返回，否则向 `decision.messages` 追加一条 user message。循环的其他部分不做任何改动。

检索流程为：改写（一次模型调用，可能回答 `need_retrieval: false` 从而跳过其余步骤）、跨来源扇出、以 K = 60 的加权 Reciprocal Rank Fusion 融合、为仅带元数据的候选补全正文、gate、渲染。

**融合按位次排序，而非按分数。** 本地 BM25 分数与目录质量分不是可比的数值，因此合并使用每条命中在其自身来源内的排名。这正是 gate 属于必需而非优化的原因：每个来源的最佳命中无论匹配多弱都会进入候选短名单，所以没有 gate 时，"今天天气怎么样"会稳定地注入本地目录排在第一的那条技能。gate 也是唯一能看出某个技能**在此处无法执行**的步骤——正文假定了某个厂商 API、`{baseDir}` 占位符或斜杠命令分发器——这是任何排序函数都检测不到的。它正是为此从 `ctx.get('tools').schemas(agent)` 接收 agent 的工具名，并被要求"什么都不选优于选一个不相关的"。

**每一步都朝着更少的技能降级，而不是朝着失败的一轮降级。** 抛异常的来源贡献空列表；超时或回复无法解析的 gate 保留其排名靠前的候选；`retrieve` 自身捕获异常并返回 `''`。检索发生在模型回答用户之前，因此其最坏情况必须只让这一轮失去技能，而不影响其他。

改写器和 gate 通过 `ctx.llm.stream` 以显式的 `provider`/`model` 组合访问模型，二者要么一起配置，要么都不配。不配置时，检索以不过滤方式运行、按排名注入前 `topK` 条——这是一个有文档记录的降级模式，而非静默选取的默认路由。终止性的 finish（包括 `max-tokens`，因为被截断的回复携带的是被截断的 JSON）会抛出，各调用方将其转为各自的回退。

被注入的消息在 `MessageSourceMap` 上声明了 `skill-search` 成员，携带 `form: 'instructions'`——这些正文是模型被期望遵循的第三方文本——以及被注入的 id，使得记录消费方可以从元数据读取模型看到了什么，而不必重新解析面向模型的文本。

本插件与 `dsh-tool-skill` 是二选一，而非分层：同时运行会把同一批技能发布两次，一次作为 schema，一次作为文本。挂载本插件的部署应禁用那一个。

## 曾考虑的替代方案

- **为 `dsh-tool-skill` 增加一个 `find_skill` 工具**——否决：它保留了那次往返，而且模型仍需自己决定去检索。大规模语料的要点恰恰在于模型并不知道里面有什么。
- **不要 gate，直接按排名注入前 K 条**——否决：已直接测得。基于位次的融合保证每个来源都贡献其最佳命中，因此无关的一轮会稳定注入无关的技能。
- **向 `GenerateOptions.purpose` 增加 `'skill-search'`**——否决：`purpose` 恰有两个消费方，都是 DeepSeek adapter 的行为（compaction 请求头、标题调用关闭 thinking）。增加一个没有消费方的第三个值属于无归属的公开选择；这些请求不设该字段。
- **通过 `dsh-skill` 的 provider 注册表接入这些来源**——否决：该注册表回答的是目录路径上"按名称列出并加载技能"。检索需要的是每个来源带分数和排名位次的有序列表，是不同的操作集合；共用一套接口会把两边都扭曲。

## 结果

- 拥有大规模技能语料的部署可以逐轮注入相关正文，而不必发布一份模型必须先读的目录。
- 注入点之前的 KV cache 前缀保持可复用；从被注入的消息往后的后缀在选择变化时改变。
- 每个执行检索的轮次产生两次会话之外的辅助模型调用。
- 23 个包内测试覆盖分词器、BM25、融合（位次优先于分数、跨来源提升、同名冲突）、gate（选择、空选择、工具清单、传输失败时的回退、带围栏的回复）、改写器（不检索裁决、无法解析的回复、空查询）、本地扫描器，以及端到端的 engine。

## 已知缺口

记录在[包 README](../README.md#known-limitations-and-deferred-work) 中：目录 bundle 从不下载、检索决策不是 session event、本地扫描在进程生命周期内缓存、以及一条路由服务两次模型调用。目前还没有经由真实可运行示例的无密钥快照——该插件尚未进入任何交付 bundle，为挂载它的部署补上快照是下一步。
