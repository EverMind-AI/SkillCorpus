- **Retrieval path**: `auto` — memory-provider `prefetch`; `on_demand` — the
  provider's `get_tool_schemas` / `handle_tool_call` pair, folded into the
  agent's own tool surface by the host.
- **Retrieved skill**: `pdf-tables`, local source.
- **P1 `on_demand` reply carried no fixture fact, and that is a PASS.** The
  tool returned the body; the model answered the question it was asked without
  quoting a convention nobody asked for. This run is the reason P1 does not
  assert on the reply — see `cases.md`.
- **Known host limitation**: Hermes caps an external provider's `prefetch` at
  **8 seconds**, in the host, whatever `timeout_s` the plugin config asks for.
  The rewriter is one model call and against this deployment spends more than
  that, so under the host default `auto` delivers nothing. The run above raised
  the cap to 300s. **On an unmodified Hermes with a reasoning model, `auto` is
  effectively unusable**; either raise the host cap or set `rewrite: false`.

| P2 | `auto` | No | Yes | No | Yes | Yes | PASS (13s) |

| P3 | `auto` | No | No | No | No | No | PASS (3s) |
| P3 | `on_demand` | Yes | No | No | No | No | PASS (2s) |

- **Retrieval path**: `auto` — the `skills` context segment, replacing the
  host's own stage; `on_demand` — `contributes.tools`, returning a subclass of
  the host's `Tool` so `to_schema` / `cast_params` / `validate_params` /
  `display_call` all come from the ABC.
- **`auto` ran on a patched host and its PASS is not public Raven support.**
  The `[[plugin.contributes.context_segments]]` slot, and the
  `build_plugin_segments` / `AgentLoop(plugin_segments=...)` wiring behind it,
  are not upstream — not on GitLab, not on GitHub, and no open MR adds them.
  Raven ignores manifest keys it does not know, so on a stock Raven
  `mode: auto` is silently inert. The script reports BLOCKED there, and did so
  on the first attempt of this run before the patched checkout was used.
- **`on_demand` does not depend on the patch.** `contributes.tools` is an
  upstream slot.
- **On-demand has no host-supplied model channel.** `build_plugin_tools` passes
  no provider, so the rewriter and gate run on the endpoint in the plugin's own
  `model_base_url` / `model_api_key`. Both were configured here; without them
  the rewriter degrades to the raw query rather than failing.

## OpenClaw 2.0

```text
Host:            openclaw 2026.8.1 (npm, branded 2.0)
Install method:  plugin registered as a context engine, with all four capability
                 gates granted (see below)
```

| Case | Mode | Retrieval path | Tool called | Result |
| --- | --- | --- | --- | --- |
| P1 | `auto` | context engine `assemble` | No | PASS |
| P1 | `on_demand` | native `registerTool` | Yes | PASS |
| P2 | `on_demand` | native `registerTool` | Yes | PASS |

- **2.0 needs a different package, not a flag.** The `before_prompt_build` hook
  the 1.x plugin is built on never fires under `agent --local`; through the
  gateway it fires but `prependContext` is dropped. `plugin-openclaw2` occupies
  the context-engine slot instead.
- **Four silent gates.** Retrieval is inert, without an error, unless all of
  `hooks.allowConversationAccess`, `hooks.allowPromptInjection`,
  `--accept-capabilities` and `plugins.slots.contextEngine` are set. The host
  also requires `info.transcriptSemantics.currentTurnFence` and
  `turnAdvancementIdempotency` **together with** a real `commitTurn` — it
  checks both before trusting durable turn advancement.
- **Instruction-shaped fixtures do not work on this host.** A skill body that
  tells the model to reply with a token is read as prompt injection and
  refused. This is why the corpus carries facts and the prompts ask questions
  those facts answer.
- **Not executed against the standardised corpus** — same as OpenClaw 1.x, same
  reason, same open work. There is no headless script: the four gates and a
  running gateway make this a manual case.

## WorkBuddy

```text
Host:            WorkBuddy 5.3.13 (desktop)
Install method:  standard plugin marketplace
Result:          BLOCKED for 0.3.0
```

| Case | Mode | Result |
| --- | --- | --- |
| all | `auto` | BLOCKED — last real-host run was at `e337cfa` |
| all | `on_demand` | BLOCKED — last real-host run was at `e337cfa` |

WorkBuddy is a desktop application; this branch's author has no install to
drive, so its rows come from the maintainer. That run was at **`e337cfa`**,
which **predates the MCP lifecycle fix**, so it does not certify the shipped
0.3.0 and is recorded as BLOCKED rather than PASS.

What the fix changed, and therefore what a real-host run has to re-check:
through `e337cfa` the MCP entry point served stdin only in `on_demand`, so with
`mode: auto` the statically declared server started and exited 0 immediately.
The manifest cannot withdraw a declared MCP server, so the host kept launching
one that died. It now serves in both modes and answers `tools/list` with an
empty array in `auto`.

What *is* verified at `e9be3de`, without the host:

- the shipped `dist/mcp.mjs` spawned as a real child process, spoken to over a
  pipe in JSON-RPC, returning a skill through the real engine;
- the process stays up in **both** modes;
- `tools/list` answers per mode — the tool in `on_demand`, an empty array in
  `auto`;
- a `tools/call` arriving in `auto` is refused rather than served.

That is a **spawned-process test, not a host test**. It says nothing about
whether WorkBuddy launches the server, or with what arguments. In particular
the `mcpServers` declaration shape is still unproven: the host wants an
absolute `args[0]`, the manifest writes
`${CODEBUDDY_PLUGIN_ROOT}/dist/mcp.mjs`, and while
`expandBracedEnvReferences` exists in the spawn path, its use on MCP args was
never confirmed. **This is the single highest-value remaining check.**

Follow the split verification in
[`plugin-workbuddy/INSTALL.agent.md`](../../plugin-workbuddy/INSTALL.agent.md);
the older notes check the hook log, which is an `auto`-mode check and not a
completion standard for the default.
