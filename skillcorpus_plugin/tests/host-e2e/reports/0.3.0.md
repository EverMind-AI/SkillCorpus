- **Retrieval path**: `auto` — memory-provider `prefetch`; `on_demand` — the

- **Retrieved skill**: `pdf-tables`, local source.

- **Known host limitation**: Hermes caps an external provider's `prefetch` at
  **8 seconds**, in the host, whatever `timeout_s` the plugin config asks for.

  the cap to 300s. **On an unmodified Hermes with a reasoning model, `auto` is
  effectively unusable**; either raise the host cap or set `rewrite: false`.

  The `[[plugin.contributes.context_segments]]` slot, and the

  on the first attempt of this run before the patched checkout was used.

  upstream slot.
- **On-demand has no host-supplied model channel.** `build_plugin_tools` passes
  no provider, so the rewriter and gate run on the endpoint in the plugin's own
  `model_base_url` / `model_api_key`. Both were configured here; without them
  the rewriter degrades to the raw query rather than failing.

| P3 | `on_demand` | Yes | No | No | No | No | PASS (10s) |

- **Retrieval path**: `auto` — the context engine's `assemble`; `on_demand` —
  the host's native `registerTool`.
- **`skill_search` queries**, verbatim from the transcript: P1 "extract tables
  from scanned PDF invoice", P2 "extract tables from a scanned PDF invoice".
- **How `auto` was established.** Same method as 1.x, and it has to be: the
  assembled context is not persisted. The evidence is the model's opening
  move, before any tool result existed — a `read` on
  `/tmp/skillsearch-e2e-601cmff9/skills/pdf-tables/SKILL.md`, a randomly named
  directory this harness had just created. Nothing else in the turn named it.
- **2.0 needs a different package, not a flag.** The `before_prompt_build` hook
  the 1.x plugin is built on never fires under `agent --local`; through the
  gateway it fires but `prependContext` is dropped. `plugin-openclaw2` occupies
  the context-engine slot instead.
- **Silent gates, and one of them is easy to write in the wrong place.**
  Retrieval is inert, without an error, unless
  `plugins.entries.skillsearch.hooks.allowConversationAccess`,
  `...hooks.allowPromptInjection` and `plugins.slots.contextEngine` are all
  set. The two grants belong to the **plugin entry**, not a top-level `hooks`
  block; written at the top level the host rejects the whole config as
  `Unrecognized keys`, which at least fails loudly. `--accept-capabilities`
  covers the run-level acceptance where a launcher needs it. The host also
  requires `info.transcriptSemantics.currentTurnFence` and
  `turnAdvancementIdempotency` **together with** a real `commitTurn` — it
  checks both before trusting durable turn advancement.
- **Instruction-shaped fixtures do not work on this host.** A skill body that
  tells the model to reply with a token is read as prompt injection and
  refused. This is why the corpus carries facts and the prompts ask questions
  those facts answer.
- **P1 `on_demand` carried no fixture fact in the reply, and that is a PASS** —
  the same observation as on Hermes, and the reason P1 does not assert on the
  reply. P2 in the same mode does, and did.

```text

Install method:  standard plugin marketplace
Bundle tested:   the current branch, i.e. including the MCP lifecycle fix
Tested by:       the maintainer, by hand
```

| Case | Mode | Retrieval path | Tool called | Result |
| --- | --- | --- | --- | --- |
| P1 | `auto` | `UserPromptSubmit` hook injection | No | PASS |
| P1 | `on_demand` | local stdio MCP, `skill_search` | Yes | PASS |

- **Both modes verified on a real install, on the shipped bundle.** In
  `on_demand` the model was offered `skill_search` and called it; in `auto` the
  hook injected and no tool call happened.
- **This is a manual result and reads differently from the rows above.** The
  other five hosts are script output with the transcript attached; this one is
  a maintainer's observation. It is recorded as PASS because it was made on
  this branch's bundle and covered both modes — not because it carries the same
  evidence trail. Anyone re-running it should follow the split verification in
  [`plugin-workbuddy/INSTALL.agent.md`](../../plugin-workbuddy/INSTALL.agent.md)
  and record what they saw.
- **The lifecycle fix is what made this row possible.** Through `e337cfa` the
  MCP entry point served stdin only in `on_demand`, so with `mode: auto` the
  statically declared server started and exited 0 immediately. The manifest
  cannot withdraw a declared MCP server, so the host kept launching one that
  died — a failed entry or restart churn beside a hook path that was working
  fine. It now serves in both modes and answers `tools/list` with an empty
  array in `auto`. The earlier maintainer run predated this and is superseded.

What the automated suite adds, and what it does not:

- the shipped `dist/mcp.mjs` spawned as a real child process, spoken to over a
  pipe in JSON-RPC, returning a skill through the real engine;
- the process stays up in **both** modes;
- `tools/list` answers per mode — the tool in `on_demand`, an empty array in
  `auto`;
- a `tools/call` arriving in `auto` is refused rather than served.

That is a **spawned-process test, not a host test**, and it stays listed
separately for that reason: it proves the bundle speaks the protocol, not that
WorkBuddy launches it. The manual run above is what covers the launch. What
neither establishes on its own is the `mcpServers` **declaration shape** — the
host wants an absolute `args[0]`, the manifest writes
`${CODEBUDDY_PLUGIN_ROOT}/dist/mcp.mjs`, and `expandBracedEnvReferences` exists
in the spawn path but was never observed being applied to MCP args. The
on-demand run passing is strong circumstantial evidence that it does expand,
since the server has to start for the tool to appear; it has not been read off
the host directly.
